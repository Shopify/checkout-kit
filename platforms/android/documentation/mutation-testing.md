# Kotlin mutation testing

This opt-in workflow uses [PIT](https://pitest.org/) to mutate compiled production
Kotlin bytecode and check whether existing tests detect the changes. Unlike
manually editing a source file, PIT generates and executes mutations automatically.
It does not rewrite the source tree.

## Run

With the normal Android development environment provisioned (`dev up`), run from
this repository's root:

```sh
shadowenv exec -- /opt/dev/bin/dev android test mutation
```

Or from `platforms/android`:

```sh
shadowenv exec -- ./gradlew :shopify-checkout:mutationTest -PmutationTest=true --console=plain
```

The task compiles the debug unit-test sources, verifies that the published
protocol dependency is selected, and runs PIT's baseline coverage analysis before
executing mutations. The PIT version is pinned in `gradle/libs.versions.toml`.
The first run downloads tooling and may need to compile the SDK; later runs are
much faster. No emulator is required.

Open the generated report:

```text
platforms/android/shopify-checkout/build/reports/pitest/index.html
```

Machine-readable results are in `mutations.xml` in the same directory. Reports
are local build outputs; do not commit them. Read reports only after a successful
run, as a failed run may leave results from a previous invocation.

## Scope

Production targets:

- `CheckoutMessageIngressPolicy`
- `OriginAllowlist`

Existing test classes:

- `CheckoutMessageIngressPolicyTest`
- `OriginAllowlistTest`

These are plain JUnit tests of message-admission rules. The task uses the Android
module's compiled classes and unit-test classpath, but **does not establish PIT
compatibility with Robolectric tests or measure the entire SDK**. Keep this scope
targeted. Expanding it requires checking the new tests' unmutated baseline and
runtime requirements first.

`mutation-testing.gradle` invokes PIT's command-line runner directly. It uses Gradle's
existing compiler outputs and test classpath rather than adding a Java source set
or relying on a Gradle PIT plugin's Android support. Tooling is loaded only with
`-PmutationTest=true`. Normal `test`, `check`, builds, and publication do not run
PIT or resolve its tooling configuration. No mutation-score CI gate is added.

## Example: improving the selected tests

With the pinned toolchain and targets, the initial run and the added behavioural
cases produced:

| Result | Initial tests | After additions |
| --- | ---: | ---: |
| Generated | 36 | 36 |
| Killed | 29 | 34 |
| Survived | 4 | 2 |
| No coverage | 3 | 0 |

The new cases assert that:

- Disabled origin validation (empty configuration or `*`) does not accidentally
  enforce the enabled-validation port-zero rule.
- Malformed origins are rejected with `ORIGIN_NOT_ALLOWED`, rather than throwing
  while parsing transport metadata.
- HTTPS URL classification accepts valid HTTPS URLs and rejects HTTP, malformed,
  unsupported-scheme, and credential-bearing URLs.

The two remaining survivors map to Kotlin's inlined `any` empty-collection fast
path in `OriginAllowlist.isAllowed`. Bytecode inspection shows a collection/type
check and an `isEmpty` shortcut before the iterator loop. Bypassing either
shortcut still gives the same result through iteration for normal, contract-
conforming lists. Do not add tests against deliberately inconsistent collection
implementations just to kill these mutants. They remain visible in the report;
no suppression or score gate hides them.

Counts can change with compiler or PIT upgrades. The primary value is the
behavioural counterexample and its killing test, not a repository-wide score.

## Team walkthrough

1. Run the command and open the report.
2. Inspect a **killed** mutant: which behaviour changed, and which test caught it?
3. Inspect a **surviving** mutant: find an input that distinguishes it from the
   original before proposing a test. A survivor is not automatically a defect.
4. Inspect **no coverage**: the selected tests did not execute that code. This is
   a statement about this task's scope, not necessarily all repository tests.
5. If a meaningful gap is found, add a behavioural test, run it normally, then
   rerun PIT to demonstrate that the mutant is now killed.

Baseline test failures and tooling errors must not be counted as successful
mutation detection. The score threshold is zero for exploration; baseline and
startup failures still fail the command. Also inspect timeout, non-viable, and
run-error statuses in the report rather than treating command success or every
non-survivor as proof that an assertion caught a fault.

PIT's named `DEFAULTS` mutator group and built-in filters are used. No additional Kotlin
mutation/filtering plugin is installed. Kotlin-generated bytecode, redundant
conditions, and equivalent mutations can affect the result; source-line mappings
may also point to compiler-generated code. Review survivors rather than adding
implementation-coupled tests or suppressions solely to reach 100%.
